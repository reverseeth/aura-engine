01O que é a Aura

A Aura é um sistema de duas partes pra construir e escalar marcas de ecommerce dentro do Claude Code, a CLI da Anthropic:

  • Base de Conhecimento Aura — um servidor MCP remoto (ferramenta search_knowledge) que guarda os frameworks especialistas em que o raciocínio da Aura é construído (Schwartz, Hopkins, Hormozi, Cialdini, Sugarman, Ogilvy, Caples, mais metodologia original sobre construção de oferta, Meta Ads científico e produção de criativos). Conectada uma vez via Settings do Claude; consultada silenciosamente dentro de toda skill que precisa fundamentar uma decisão.
  • Aura Engine — um projeto (clonado em ~/aura-engine) contendo 15 skills, libs de suporte, rules, hooks e templates. Skills se ativam por contexto: o membro descreve o que precisa, a Aura identifica em qual fase está, e a skill apropriada roda.
Princípio central: cada fase produz artefatos versionados em /workspace/[product-slug]/ que alimentam a próxima. Nada é jogado fora — copy bebe da pesquisa, criativos bebem da copy, ads bebem dos criativos, retenção bebe da venda.
Filosofia de output: todo arquivo .md que a Aura escreve tem um .html companion no mesmo diretório. O .md é a fonte que a AI lê na fase seguinte; o .html é a versão que o membro abre no browser pra ler com calma.
02A Base de Conhecimento Aura (search_knowledge)

A Base de Conhecimento é a camada de expertise profunda que sustenta o raciocínio da Aura. Vive como um servidor MCP remoto, indexado e consultável por uma única chamada de tool.

Como o membro conecta

Conexão acontece uma vez por dispositivo, e fica permanente até o membro remover.

  • Claude Desktop: Settings → Integrations → Add Custom Integration → Nome Aura → URL https://aura-mcp-production.up.railway.app/mcp → Add
  • Claude Code (terminal): claude mcp add --transport http aura https://aura-mcp-production.up.railway.app/mcp

Instruções completas com screenshots ficam em Aura.html (português) e Aura-en.html (inglês) — os tutoriais de instalação que acompanham o sistema.

O que tem dentro

A base agrega a literatura fundacional de direct-response e ecommerce mais metodologia original. Quando uma skill precisa fundamentar uma decisão, consulta com frases de intent específica. Exemplos por domínio:

Toda busca roda com deep=true pra resultados completos. Múltiplas buscas por tópico são normais — queries únicas raramente cobrem uma área inteira.

Como se comporta dentro das skills
  • Sempre consultada, nunca nomeada. Skills consultam a base sempre que precisam fundamentar uma recomendação, mas nunca avisam ao membro que estão buscando, nunca citam a fonte e nunca namedropam o material de curso por trás.
  • Autores e livros são citáveis. Schwartz, Cialdini, Hopkins, Hormozi, Sugarman, Ogilvy, Caples etc. podem ser referenciados diretamente quando relevante — são conhecimento público.
  • Fontes internas não. Nomes específicos de cursos, vaults, programas internos nunca aparecem pro membro.
Por que importa: a Base de Conhecimento é o que faz o output da Aura ser específico em vez de genérico. Sem ela, o sistema cairia no mesmo conselho superficial de marketing que um LLM sozinho produz. Com ela, toda recomendação é ancorada em metodologia comprovada de direct-response.
03Arquitetura geral
~/aura-engine/ ← clonado de github.com/reverseeth/aura-engine ├── .claude/ │ ├── CLAUDE.md ← instruções fundamentais (idioma, copy rules, dual output, MCP) │ ├── OVERVIEW.md / .html ← companion interno deste documento │ ├── skills/ ← 17 arquivos .md (skills 00-14, com 07a/07b/07c) │ ├── lib/ ← libs reutilizáveis chamadas pelas skills │ ├── rules/ ← diretrizes auto-carregadas por contexto │ ├── hooks/ ← scripts que rodam em eventos do Claude Code │ ├── templates/ ← templates HTML, schemas JSON, snippet do logo SVG │ └── settings.json ← config do Claude Code (hooks, permissions) │ ├── AGENTS.md ← mirror local do CLAUDE.md (gitignored, específico do membro) └── workspace/ ← criado pela skill 00, organizado por produto ├── profile.md ← contexto do membro (budget, ESP, tools, mercado, idioma) └── [product-slug]/ ├── manifest.json ← single source of truth do estado do produto └── 01..14 ← artefatos versionados produzidos por cada skill
A Base de Conhecimento Aura não está nesta árvore — é um servidor MCP remoto conectado separadamente pelo membro. Engine e Base de Conhecimento são independentes: cada uma funciona sem a outra, mas juntas formam o sistema completo.
04As 15 skills (em detalhe)

Cada skill é um arquivo .md com frontmatter (nome + descrição) e corpo estruturado em ETAPAs numeradas. O Claude lê a skill, segue as etapas, e salva os artefatos prescritos. Skills estão listadas abaixo na ordem em que o membro roda em uma sessão normal.

00 Setup "setup"
Configuração da primeira vez. Pergunta o idioma preferido pra relatórios internos (pt-BR ou en), cria /workspace/ com o slug do produto, coleta contexto do membro (budget, ESP, tools, mercado) em profile.md, inicializa manifest.json, e detecta se o membro já está no meio de outro produto.
Output: manifest.json profile.md
01 Product Research "product research"
Valida produtos contra critérios (mass desire, mass urgency, mass uniqueness), aplica o framework de sophistication de Schwartz (stages 1-5), recomenda go/no-go. Se o membro ainda não tem produto, sugere opções viáveis no nicho dele.
Enrichment opcional: quando o MCP TrendTrack está conectado, a ETAPA 0.5 usa find_winning_products + search_shops + creative_inspiration_pack pra validar contra winners reais com revenue tracked, em vez de depender só dos frameworks.
Output: 01-product-research.md/html
02 Market Research "market research"
Voice of Customer (VOC) mining em Reddit, fóruns, reviews, TikTok comments. Identifica frases exatas (verbatim), mapeia distribuição de awareness (% unaware / problem / solution / product / most aware), drivers psicográficos, objeções ranqueadas por intensidade.
Por que importa: o documento mais consultado do sistema. Skills 04 (oferta), 06 (copy), 08 (criativos) leem dele pra fundamentar cada claim.
Output: 02-market-research.md/html/json
03 Competitor Analysis "competitor analysis"
Identifica 5-10 concorrentes ativos via Meta Ad Library + Similarweb. Analisa PDPs (estrutura, headlines, mecanismos, garantias, social proof). ETAPA 3C: análise profunda de criativos escalados via transcription Whisper.
Fallback chain pra páginas bloqueadas: Wayback Machine → archive.today (Google Cache foi descontinuado em set/2024 e removido da skill).
Enrichment opcional: quando o MCP TrendTrack está conectado, a ETAPA 0.5 colapsa boa parte das ETAPAs 1-3 em chamadas brief_competitor + search_shops + find_similar_shops + scan_ad — elimina necessidade de cloaker fallbacks.
Output: 03-competitor-analysis.md/html 03-creative-patterns.json
04 Offer Builder "offer"
Constrói o mecanismo único (UMP/UMS theory). ETAPA 2.5 obrigatória — Research Foundation: cada claim do mecanismo precisa de evidência rastreável. Pricing triangulado (3 âncoras: COGS, valor entregue, dor evitada), bonus stack, garantia que ataca a objeção #1, unit economics completa, 11 sanity checks antes de salvar.
Outputs críticos pras skills downstream:
  • bonuses[] array → lido pela skill 05 (bonus delivery)
  • offer_stack string → lido pela skill 06 (copy)
  • unit_economics.weighted_margin_per_order + target_cpa_primary_2x/3x → lidos pela skill 11 (ad analysis) pra detecção dinâmica de LOSER
Output: 04-offer.md/html/json 04-research-foundation.json
05 Bonus Delivery "bonus delivery"
Asset prep pros bonuses definidos na skill 04. Lê 04-offer.json.bonuses[]. Pra cada bonus, gera pipeline de entrega conforme delivery_trigger (post-purchase, on-signup, day-7, on-first-reorder). Templates por tipo: digital guide → PDF, community access → Circle invite, video series → Wistia hosted, etc.
Output: 05-bonus-delivery/[bonus-id]/ com assets + instruções de upload
06 Copy Engine "copy"
Headlines (o processo adapta o "Process of 100" de Caples ao volume necessário). Lead types selecionados por awareness stage (Story, Problem-Solution, Secret, Offer, Proclamation, Direct). Hero sections apropriadas ao tipo de página, bullets, social proof, FAQ, urgency, email hooks (que a skill 13 reutiliza). 8 sweeps de revisão: clarity, VOC, specificity, flow, objection, CTA, originality, compliance.
Output: 06-copy.md/html/json (lido pela cadeia 07 page)
07 Page Engine — cadeia 07a → 07b → 07c "page"
Por que está dividida em três: a versão monolítica tinha 1055 linhas. Quebrar melhora performance e permite o membro iterar em uma fase específica sem regenerar tudo.
07a — Page Planning
  • Pre-flight (skill 06 completa, manifest válido)
  • Detecta tipo de página (advertorial vs landing vs hybrid)
  • Brand discovery + referência visual opcional
  • Orquestração do design system: cor → typography → spacing → grid → tokens
  • Camada visual blueprint opcional via Google Stitch (opt-in)
  • Output: 07-page/07-design-system.md + 07-plan.md + 07-plan.json
07b — Page Sections
  • Gera 3 variantes de hero (membro escolhe A/B/C)
  • Converte pro padrão de inline-blocks no schema Shopify
  • Replica padrão pras demais sections do plano
  • UX writing pass + self-critique (heurísticas Nielsen + WCAG 2.1 AA)
  • Validação Liquid via shopify-plugin:shopify-liquid com retry logic
  • Output: arquivos .liquid em <staging>/sections/ + 07-sections-report.md
07c — Page Deploy
  • GATE Skill 09 (consistency audit) no pre-flight: aborta em BLOCK
  • Cria templates/page.[produto].json com blocks pré-populados
  • Validação OBRIGATÓRIA de blocks (não-vazios, types válidos)
  • Deploy seguro: duplicate theme → pull → cp → push --nodelete
  • Smoke test pós-push (curl no storefront, grep marker)
  • Output: preview URLs + 07-deploy-report.md/json
Page registry: quando múltiplas páginas existem pra um mesmo produto (ex: v1 narrative + v2 editorial), o 07-page/page-registry.md centraliza URL, frame, opening line, e detalhes de message-match ad→page. Briefings de criativo referenciam páginas por slug — atualizar uma página só requer editar o registry.
08 Creative Engine "creatives"
Pipeline completo de geração de criativos. Por conceito: 3 format variants (Real Cuts / Hyper Motion / AI UGC) compartilhando um body BRIDGE → HOLD → CTA, com hook único por variante.
  • ETAPA 1: detecta material disponível + creator archetype
  • ETAPA 2: calcula quantidade de conceitos por stage do membro (3-4 starter, 6-8 validating, 10-15 scaling)
  • ETAPA 3: gera ângulos nas 3 verticais (problema, resultado, identidade)
  • ETAPA 4.5: regras estruturais globais (VOC traceability, hook rotation, swap viability)
  • ETAPA 5: briefings completos por conceito
  • ETAPA 5.7: prompts production-ready (Higgsfield + GPT Image 2.0)
  • ETAPA 6: LP congruency mapping (pra qual página cada conceito direciona)
  • ETAPA 7: hooks bank (10 alternativas pra iterações futuras)
  • ETAPA 7.4: carrega DNA aprendido do registry (cross-product learning)
  • ETAPA 7.5: compliance pre-flight (rule 8b)
  • ETAPA 7.6: extração de DNA pro registry (silent — alimenta lib/creative-dna/registry.py)
  • ETAPA 8: resumo de produção
Enrichment opcional: quando o MCP TrendTrack está conectado, o Hooks Bank é alimentado com archetypes vencedores reais via creative_inspiration_pack + scan_ad.
Output: 08-creatives.json + 1 briefing .md por conceito (com .html companion)
09 Consistency Audit "consistency audit" "audit"
Cross-phase drift detection: confirma que mecanismo, awareness stage, VOC e oferta concordam entre todos os artefatos (skills 02 → 03 → 04 → 06 → 07 → 08). Verifica VOC traceability (frases na copy/ads vêm da pesquisa). Verifica promise↔config (promessas das páginas batem com config da loja Shopify).
Como vira gate: skills 07c, 10 e 13 leem o JSON dessa skill no pre-flight. Se launch_recommendation == "BLOCK", abortam. Drift entre fases para de chegar em produção.
Output: 09-consistency-audit.md/html/json com launch_recommendation: "BLOCK" | "CAUTION" | "GO"
10 Ad Strategy "ad strategy"
Pre-flight pra pré-requisitos (Pixel, CAPI, produto live, criativos prontos). Estrutura de campanha (One Campaign Method). Ad sets em 3-2-2 (3 conceitos × 2 hooks × 2 thumbnails). Naming convention padrão (campaign_name salvo no manifest pra skill 11 cruzar). Árvore de decisão por timeline (dia 1/3/7/14). Performance Gate Scaling (PGS) automático. Inclui árvore de decisão de analytics (Meta App / Wetracked / Triple Whale / Aimerce) ajustada ao stage do membro.
GATE Skill 09 roda no pre-flight. Aborta em BLOCK. Drift entre criativos / copy / oferta vira disapproval ou ad↔landing mismatch.
Output: 10-ad-strategy.md/html/json + manifest 10_campaign_name
11 Ad Analysis "ad analysis"
Análise 4Pi (Spend, Frequency, CPM, Cost per Result). Detecção dinâmica de LOSER (lê 04-offer.json.unit_economics.weighted_margin_per_order + target_cpa_primary_2x/3x). 19-Point Loser Diagnostic em 4 camadas (targeting, hook, copy, oferta). Identifica WINNERs (CPA < target × 0.7, spend > $300, idade > 5 dias). Recomenda iterar vs escalar.
Enrichment opcional: quando o MCP TrendTrack está conectado, scan_ad faz benchmark dos winners contra o mercado e daily_radar monitora movimentos dos concorrentes.
Output: 11-analysis/[timestamp].json + 11-analysis/latest.json (handoff pras skills 12 e 14)
12 Scale Engine "scale"
Pre-flight (skills 10 + 11 completas). Vertical scaling (PGS 5% rule). Horizontal scaling (novos ad sets, novos placements, novos angles). Champion promotion (Post ID dedicado). Diversification por stage (Tier 1/2/3+).
Output: 12-scale/[timestamp].md + plano de execução
13 Retention Engine "retention" "email flows" "klaviyo"
Pre-flight: ESP identificado (Klaviyo / Omnisend / MailerLite), ≥50 compras no histórico. Fluxos base: welcome series, abandoned cart, post-purchase, win-back, replenishment. Cada fluxo adapta ao produto (lê 04-offer.md pra reorder rate, período de garantia, bonuses entregáveis).
GATE Skill 09 no pre-flight: aborta em BLOCK. Fluxos de email herdariam qualquer drift detectado (mecanismo divergente, VOC não rastreada, oferta diferente) e propagariam inconsistência pra base de subscribers.
Enrichment opcional: quando o MCP TrendTrack está conectado, analyze_shop_emails calibra o timing dos fluxos contra padrões reais de cadência/subject das marcas concorrentes.
Output: 13-retention/[fluxo]/email-N.html + flow metadata + relatório operacional
14 Content Recycler "content recycler" "recycle [id]" "recycle winner"
Lê um criativo winner (input direto OU auto-detectado via 11-analysis/latest.json.winners[]). Extrai essência (big idea, hook, mechanism, avatar, voice) em essence.json. Gera 9 derivadas em formatos diferentes: advertorial, email sequence, organic TikTok, blog SEO, Pinterest carousel, YouTube preroll, SMS, package insert, podcast ad. Compliance pre-flight em cada derivada (severity ≥ high dispara auto-rewrite).
Output: 14-recycled/[source-id]/ com 9 .md + 9 .html + README.md/html + essence.json + compliance-log.json

10Convenções operacionais
Idioma e estilo (CLAUDE.md rule 0)
  • Relatórios internos: no idioma escolhido durante setup (pt-BR ou en) — claro, direto, sem jargão acadêmico. Termos de marketing ficam em inglês quando naturais (VOC, hook, CTA, ROAS).
  • Copy pro consumidor final: sempre em inglês (mercado US padrão), independente do idioma de relatório interno. A escolha de idioma do membro nunca afeta copy pública de ad ou página.
Uso da Base de Conhecimento (CLAUDE.md rules 1-3)
  • Skills consultam search_knowledge silenciosamente. Nunca avisam ao membro que têm uma base de conhecimento, MCP ou fonte externa.
  • Nomes de cursos e títulos de programas internos nunca são citados. Livros e autores (Schwartz, Cialdini, Hopkins, Hormozi, Sugarman, Ogilvy, Caples) podem ser referenciados diretamente quando relevante.
  • Múltiplas buscas por tópico são normais — queries únicas raramente cobrem uma área completamente.
Dual output (.md + .html) — CLAUDE.md rule 6b
  • .md é a fonte que a AI lê na fase seguinte
  • .html é a versão humana (browser)
  • HTML usa o design system do aura-report-template.html + logo SVG Aura no topo
Logo SVG obrigatório
  • Bloco SVG copiado literalmente de aura-logo-snippet.html
  • Proibido substituir por texto "AURA" / "Aura Engine" / qualquer variação textual
  • Sem fallback: se não conseguir copiar, parar e perguntar
Ícones SVG, nunca emojis em UI consumidor — CLAUDE.md rule 7
  • PDPs, landings, checkouts: SVGs inline (Lucide, Heroicons, Phosphor, custom)
  • Specs: 16-18px em listas, 20-24px em feature blocks, stroke 1.5-2px
  • EXCEÇÃO: relatórios internos da Aura em /workspace/ podem usar emojis pra velocidade de escaneamento
Copy rules — CLAUDE.md rule 8
  • 8a — minimizar em-dashes (—). Zero em headlines. ≤2 em copy longa.
  • 8b — substituições automáticas de palavras ad-flag pra política Meta/TikTok (Botox → "the appointment", Filler → "injectables", "Weight loss" → "transformation", etc.)
Self-audit silencioso obrigatório — CLAUDE.md rule 9

Antes de declarar qualquer skill ou tarefa importante "completa", 5 gates mentais rodam silenciosamente: cross-artifact consistency, erros factuais, gaps, qualidade, alinhamento com rules. Tudo que for achado errado, faltando ou fraco dentro do escopo da skill é corrigido inline sem mencionar. O membro só vê a versão corrigida. Surface só quando o issue exige decisão do membro (fontes conflitantes, fix que expandiria escopo, input externo faltando). Blocos visíveis de "self-audit results" são proibidos.

Integrações MCP opcionais — CLAUDE.md rule 10

A Aura detecta MCPs externos conectados pelo membro (Claude Desktop ou Code) e enriquece skills automaticamente quando disponíveis. Meta MCP (cascade oficial → Pipeboard → manual) e TrendTrack MCP são os casos principais (ver seção 12). Outros MCPs futuros (Klaviyo oficial, Shopify Dev MCP, Stripe) seguem o mesmo padrão: detecção automática + fallback silencioso quando ausente.

11Memória persistente — registry creative-dna

Cross-product learning. A skill 08 (creatives) salva DNA toda vez que executa: hook archetypes que funcionaram, voice signatures, padrões estruturais. A próxima execução em outro produto lê esse registry e adapta sem reinventar.

Read/write: via lib/creative-dna/registry.py. Skill 08 chama em silent steps (ETAPA 7.4 carrega, ETAPA 7.6 escreve).
O que NÃO entra no registry: dados específicos do produto (nomes, claims, preços). Só padrões abstratos. O registry não tem PII nem info proprietária de produto.

13Como rodar uma sessão completa do zero

Ordem canônica pra um produto novo:

  1. setup — cria workspace, profile, manifest
  2. product research — valida o produto, define vertical
  3. market research — VOC, awareness, drivers (artefato mais consultado)
  4. competitor analysis — 5-10 concorrentes, padrões, gaps
  5. offer — mecanismo, pricing, stack, garantia, unit economics
  6. bonus delivery — asset prep pros bonuses definidos acima (PDFs, emails, Circle invites)
  7. copy — copy completa pra cada section da página
  8. page — 07a (planning) → 07b (sections) → 07c (deploy)
  9. creatives — 6-15 conceitos com briefings completos
  10. consistency audit — cross-phase drift check (gate antes do launch)
  11. ad strategy — estrutura de campanha, naming, PGS
  12. — LAUNCH —
  13. ad analysis (depois de 3-7 dias) — 4Pi, diagnóstico, decisões
  14. scale (depois que winners emergem) — vertical + horizontal
  15. retention (≥50 compras) — fluxos Klaviyo
  16. content recycler (depois de winner consolidado) — 9 derivadas do criativo top
Cada skill faz pre-flight da anterior. Se algum artefato falta, a skill oferece fallback (rule emergency-escape-paths — ES1).
Iteration loop normal: depois de cada launch, ad analysis + iteração de creative ou copy é o ciclo. Skill 09 (consistency audit) reroda antes de qualquer relaunch crítico.
